## 1. Why

Two problems were bundled in the original proposal. They have different evidence and different
solutions; v0.4 solves both with one engine.

| | P1 — copied engine | P2 — commands run outside the gate |
| --- | --- | --- |
| What | Every target repository receives ~3,100 lines of bash (`gate.sh`, `harness-check.sh`, `lib/`, 25+ sensors) [fact]. Each engine fix must be re-copied; `harness-check` exists partly to detect drift between copies | The agent runs build, test and lint commands by itself and improvises filters (`\| tail`, `\| grep`) |
| Evidence | Code size and drift checks [fact] | Local transcripts, §1.1 [fact] |
| Solution | One versioned binary driven by a declarative file | The same binary runs commands with a reliable verdict, consistent reduction and retained evidence |

### 1.1 What the transcripts measured (2026-11-03)

45 real sessions (aether-labs/plugins, finq-*), ~1.7 M tokens of Bash output; eval sandboxes excluded.
Classification is heuristic over the command text; the corpus has almost no heavy JVM builds, so a
verbose Maven/Gradle build remains unmeasured.

| Finding | Number |
| --- | --- |
| Bash output as a share of all tool-result volume | 46–67 % per project |
| …of which file reading through `cat`/`sed`/`grep`/`for` loops | the bulk (~1.0 M tokens) |
| Build/test/lint/validate invocations (leading command) | 139 calls, **38 k tokens total, mean 270, none above 2 k** |
| …piped into `tail`/`head`/`grep` with no `pipefail`, `PIPESTATUS` or rc capture | **63 %** — the tool's exit code was lost |
| …re-run within the next 2 calls with a different filter | **14 %** — the first filter hid what mattered |
| Large outputs Claude Code itself persisted to a file ("Output too large … Full output saved to") | 28+ |

**Consequence [owner, D53]:** the engine's primary goal is **a deterministic verdict, traceable
evidence and no re-runs**. Context reduction is a consequence, not the goal. Generic "full output on
demand" already exists in Claude Code's runtime; `kh` adds what the runtime cannot: a verdict that
never depends on a pipe or a model, a reduction that is the same every time, an execution ID, and
evidence tied to the exact tree state — for any agent.

## 2. Goals, non-goals, anti-goals

**Goals**
- A single static binary, `kh`, that runs a repository's declared scripts and gates locally and
  returns a structured verdict with a pointer to the full evidence.
- Nothing of keel's engine copied into a repository beyond a small wrapper script and configuration.
- Results agents, hooks and humans read the same way, independent of the agent or model.

**Non-goals**
- CI. keel generates no CI workflow (D55). `kh` happens to run in CI if a team wires it; that is not
  supported or tested by keel.
- Replacing task runners (Gradle, Maven, Nx, Turborepo, mise, Task, npm scripts). Scripts call them.
- Sandboxing. The agent runtime's sandbox applies; `kh` runs as the user.
- Toolchain management (that is mise/asdf's job), capability discovery (D69), Windows outside WSL (D68).
- Migration from the bash engine: no repository has keel installed today [owner].

**Anti-goals** — the work fails even if it "works" when:
- a verdict depends on an LLM's reading of output, or a parser turns a non-zero exit into a pass;
- a missing tool, a timeout or a broken config reads as a pass;
- the agent can loosen the harness through `kh`'s own configuration without `guard` noticing;
- two repositories on one machine can affect each other's `kh` version, state or hooks (§9).

## 3. Responsibilities

| Layer | Owns | Does not own |
| --- | --- | --- |
| **`kh` (CLI)** | Executing scripts and gates; capture, timeout, retries; parsing by format; verdict; baselines; `guard`; evidence store and redaction; `kh check`; hook logic (`kh hook …`) | Judgment, proposing rules, talking to the user, installing itself into a repo |
| **keel plugin (skills)** | Inferring the stack and proposing `keel.yml`, rules and ADRs with the user's approval; installing the wrapper, lock and hooks; `scripts/keel` flow control (D70) | Running the project's checks at gate time |
| **Agent runtime adapter** (Claude Code today) | Calling `kh hook pre-tool-use` / `kh hook stop` and relaying their answers; its own sandbox; its own large-output persistence | Any verdict logic |
| **Git hook (pre-commit)** | Running `kh gate fast` on staged changes, for humans and agents alike | — |

## 4. Configuration — `.agents/keel.yml`

One file, in `.agents/` beside the rest of keel's committed configuration [owner, D56]. It works like
`package.json` scripts: a **script** is a named command; a **gate** is a named list of scripts. A
"sensor" is not a separate entity: it is a script that carries verdict metadata.

```yaml
version: 1
scripts:
  build: ./gradlew assemble                      # short form: exactly a package.json script
  test:
    run: ./gradlew test
    format: junit
    reports: build/test-results/test/*.xml
    timeout: 10m
    retries: 1
    class: correctness
    guidance: >-
      Read the failing assertion; do not change the test to the new value without an ADR.
  lint:
    run: npx eslint -f json
    files: "*.{ts,tsx}"                           # runs only if a changed file matches; files appended
    format: eslint-json
    class: heuristic
    baseline: .agents/baselines/lint.tsv
  typecheck:
    run: npx tsc --noEmit
    files: "*.{ts,tsx}"
    pass_files: false                             # the tool takes no files: whole project, only when a .ts changed
    format: errorformat
    pattern: '^(?P<file>[^(]+)\((?P<line>\d+),(?P<col>\d+)\): error (?P<rule>TS\d+): (?P<message>.*)$'
    class: correctness
  file-size:
    builtin: file-size
    limit: 300
    enforcement: ratchet
    decision: docs/adr/0003-file-size.md
    baseline: .agents/baselines/file-size.tsv
  secrets: { run: gitleaks detect --no-banner --report-format sarif --report-path {report}, format: sarif, class: security }
  legacy-check: { exec: scripts/legacy-check.sh } # escape hatch: any file obeying the line-1 contract
gates:
  fast: { scripts: [guard, secrets, typecheck, lint, file-size], changes: worktree, ceiling: 30s }
  commit: { scripts: [guard, secrets, lint], changes: staged, ceiling: 30s }
  slow: { scripts: [test], changes: branch, ceiling: 10m }
```

Rules for the file:

- **Short and expanded forms** (D56). A string is a plain command with no verdict metadata beyond the
  exit code. The map form adds `format`, `class`, `guidance`, `timeout`, `retries`, `baseline`,
  `files`, `pass_files`, `enforcement`, `decision`.
- **No implicit `pre`/`post`** (D56). Composition is explicit: a gate lists scripts.
- **`run:` is a shell string** run with `bash -o pipefail -c` from the repository root [builder].
  Pipes are discouraged in `run:`: `kh` already captures and reduces, and a pipe is how exit codes were
  lost (§1.1). `{report}` expands to a fresh path under the run's evidence directory, for tools that
  write their report to a file.
- **Change scoping follows pre-commit** (D57). `files:` is a glob over changed files: the script runs
  only if one matches, and the matching files are appended as arguments (`pass_files: true`, the
  default when `files` is set). `kh gate <name> --all` passes every tracked file matching the glob,
  split into batches under the platform's argument limit, one verdict merged from all batches. With no
  matching file, the script is a `skip` with reason "no changed files in scope" — never a silent pass
  [builder].
- **The base of a change belongs to the gate, not the script** (D57): `changes: worktree` (tracked diff
  against `HEAD` plus untracked, today's `SCOPE`), `staged` (the files in the index, for pre-commit —
  the bash engine put unstaged-only files in scope there [fact, `gate.sh:55-58`]), or `branch` (against
  `KEEL_GUARD_BASE`, else the merge-base with `origin/HEAD`, else `HEAD`, as `guard` does today).
  **`staged` narrows the file list only; tools still read file content from disk** [builder]. Hiding
  unstaged edits (stash, as the pre-commit framework does) or checking out the index into a temporary
  tree is out of v0.4: stash/restore can lose the user's work on a conflict or an interrupted run, and a
  temporary tree breaks tools that need `node_modules` or a build directory. Documented as a limitation.
- **A missing tool** [builder]: a script may declare `requires: [gitleaks]`; a required executable not
  on `PATH`, or exit 127 from `bash -c` ("command not found") with no `requires`, is a `skip` with the
  missing name and `make bootstrap` as the fix. **A `skip` of a `class: security` or
  `enforcement: mandatory` script fails the gate** (anti-goal: a missing scanner must not read as a
  green gate); any other `skip` is reported in the verdict line (`PASSED (4 of 4, 1 skipped)`) and does
  not fail it, as in v0.3.
- **`adr_dir:`** is a top-level key of `keel.yml` (default `docs/adr`, D45 kept). `kh` reads nothing
  from `.agents/state.yml`, which stays the skills' own state; "an installed harness" means
  `.agents/keel.yml` exists [builder].
- **Rule parameters live here** (D64). `.agents/rules/<id>.env`, `.agents/gate.env` and the
  `rule-env.md` contract are retired. `enforcement: mandatory | ratchet` and `decision:` (the ADR path)
  carry what the env files carried; ADRs stay in the folder `adr_dir` names.
- **Validation is strict:** unknown keys, a `builtin` that does not exist, a `format` without its
  required fields, a gate naming an unknown script, or an installed harness whose `fast` gate lacks
  `guard` — all exit 3. A JSON Schema is published for editors; `kh validate` is the authority.
- **Rule metadata are fields of the script that enforces the rule** (D64) [builder]: `decision` (ADR
  path), `doc` (the docs section anchor), `origin`, `approved_at`, `plan`, `enforcement`,
  `exceptions: [{path, until}]` (a deadline that can only shrink, D43), `exemplar`, `legacy`. A
  builtin's own parameters go under `with:` (`with: {limit: 300, include: [src/**]}`), so each builtin
  has its own strict sub-schema. A rule with no computational check (an inferential principle) is not
  in `keel.yml`: it lives in `docs/architecture.md` with `→ review:<owner>`, as D43 already says, and
  `mandatory-unsensored` warns when a principle there is marked mandatory.
- **Tool-native affected selection is preferred when it exists** (`vitest --changed`, `nx affected`,
  `turbo --filter`). That is guidance for the `build` skill when it proposes a script, not a `kh`
  feature (D73).

## 5. Execution model

```
kh run <script> [-- extra args]     one declared script
kh run -- <command…>                any command: capture, verdict from exit code, generic reduction
kh gate <name> [--all]              the gate's scripts, in order
kh show <run-id> [--failures|--full|--json]
kh measure <script>                 per-file counts as a TSV baseline on stdout (replaces KEEL_MEASURE=1);
                                    the skills write it to .agents/baselines/ with the user's approval
kh check | kh validate | kh guard | kh version
kh hook stop | kh hook pre-tool-use   (JSON on stdin; adapter entry points)
```

Per script, `kh`:

1. resolves the scope (gate `changes` + script `files`), or skips;
2. starts the command in its own process group, stdout and stderr captured into one ordered stream,
   streamed to the evidence log while it runs (redacted, §7);
3. enforces `timeout` (default 10 min [builder]): on expiry it terminates the group (SIGTERM, then
   SIGKILL after 5 s) and the status is `error`;
4. on `fail` only, retries up to `retries` times (0 by default, at most 3 [owner, D61]); a pass after a
   retry is reported as `pass (flaky: k/n)` and kept as such in the run history; `error` is never
   retried;
5. parses the output or the `reports:` files by `format`, compares with the baseline if any, and
   derives the status (§6.2);
6. writes the evidence and prints the reduced result.

Scripts run **sequentially** in v0.4 (D61); a gate's `ceiling` is checked after the run and flagged,
as today. Parallelism is a later opt-in, behind a measurement. Two gates in one repository never run at
once: `kh` takes a lock in `.agents/run/`.

### 5.1 Parsers by format, not by tool (D58)

| Format | Covers (examples) |
| --- | --- |
| `junit` | Gradle, Maven Surefire/Failsafe, pytest (`--junitxml`), vitest/jest/Playwright junit reporters |
| `sarif` | eslint (formatter), semgrep, gitleaks, ruff, CodeQL — SARIF 2.1.0, OASIS |
| `checkstyle` | Checkstyle, ktlint, detekt, many linters' checkstyle output |
| `eslint-json` | eslint's native JSON, when no SARIF formatter is installed [builder] |
| `errorformat` | Any line-oriented tool with no structured output (`tsc`, `mypy`, compilers): one named-group regex (`file`, `line`, `col`, `rule`, `severity`, `message`), multi-line continuation optional |
| none | Exit code only, generic reduction (§6.3) |

**Builtins** replace keel's own bash checks with native code: `guard`, `file-size`, `code-language`,
`folder-layout`, `pattern`, `architecture-grep`, `test-presence`, `dependencies`. External
architecture tools (ArchUnit, dependency-cruiser, import-linter) are scripts with a format (ArchUnit
reports through JUnit; dependency-cruiser and import-linter through `errorformat` or their JSON) and
keep their native baselines. **`exec:`** runs a file that obeys the line-1 contract (`id<TAB>class<TAB>status<TAB>summary`, exit 0/1/2) for what nothing above covers.

## 6. Contracts

### 6.1 Output to the agent (default: compact text)

```
test  FAIL  exit=1  4.2s  3 failed of 212  [run 20261103-142233-7f3a]
  src/test/java/foo/BarTest.java:42  BarTest.shouldX  expected 3 but was 4
  … (at most 5 findings, most severe first, then in file order)
guidance: Read the failing assertion; do not change the test to the new value without an ADR.
evidence: kh show 20261103-142233-7f3a [--failures | --full]
```

A gate prints one such block per script that did not pass, one line per script that passed, then the
verdict line `gate: fast - FAILED (1 of 5) | ceiling 30s, spent 12.4s | run 20261103-142233-7f3a`.
Output to stdout is capped at 40 lines; the cap is announced, never silent.

### 6.2 Status and verdict invariants (D59)

| Status | Meaning | Exit (`kh run`) |
| --- | --- | --- |
| `pass` | exit 0 and, if baselined, no file above its baseline; `pass (flaky: k/n)` after a retry | 0 |
| `fail` | the tool reported problems | 1 |
| `skip` | the tool is not installed, or no changed file is in scope — with the reason | 2 |
| `error` | timeout, cannot start, report file missing, unreadable or invalid config | 3 |

- The verdict comes from the exit code, the parser and the baseline. **Never from a model.**
- A parser may enrich a failure; it **never turns a non-zero exit into `pass`**. The single exception is
  a `heuristic` script with a baseline, whose status is the comparison with the baseline (contract kept
  from v0.2). `security` scripts never take a baseline.
- A parser that does not recognise the output falls back to the generic reduction and marks
  `parsed: false`; a declared `reports:` file that is missing after the run is an `error`.
- `kh gate` exits 1 if any script failed or errored, else 0; an invalid `keel.yml` or pin exits 3;
  bad usage exits 64.

### 6.3 Context reduction

Ordered, deterministic, the same every run:

1. **Structured findings first.** With a parser, the agent sees findings (`file:line rule message`),
   not console text: at most 5, ordered by severity then position, plus counts per severity.
2. **Generic reduction without a parser:** the exit code, the first 5 lines that match a fixed
   error vocabulary (`error`, `FAIL`, `Exception`, `panic`, `Traceback`, …) [builder], and the last 10
   lines. No heuristics tuned per tool.
3. **Nothing is lost:** everything else is in the evidence, one `kh show` away. The reduced output
   always prints how to get the rest.
4. `kh show <id> --failures` prints only failing findings with their surrounding log lines;
   `--full` prints the redacted log; `--json` the whole result.

### 6.4 `--json` (hooks and machines)

`{id, script, command, gate, status, exit_code, attempts, duration_ms, summary, counts{error,warning,note},
findings[{file, line, col, rule, severity, message}], parsed, baseline{file, over[]}, guidance,
evidence{dir, log, reports[]}, tree{head, diff_hash}}`. The schema is versioned with `keel.yml`'s
`version`.

## 7. Evidence, history and redaction (D60)

- **Where:** `.agents/run/runs/<id>/` (git-ignored, D39): `meta.json` (command, cwd, gate, `kh`
  version, `HEAD`, hash of the diff, exit, attempts, timings), `output.log`, `findings.json`, copies of
  the declared report files.
- **ID:** `YYYYMMDD-HHMMSS-<4 hex>`, sortable by time; a gate run has its own ID and lists its scripts'
  run IDs.
- **Retention:** the last 50 runs or 200 MB, whichever is reached first [builder]; the oldest are
  removed after each run.
- **Traceability:** `tree{head, diff_hash}` lets `kh show` and the Stop hook answer "does this result
  still describe the current tree?" without re-running.
- **Redaction, best effort [owner]:** before writing and before printing, values of environment
  variables whose names look secret (`*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*_KEY`, `*CREDENTIAL*`) and
  known patterns (AWS access keys, GitHub tokens, JWTs, `PRIVATE KEY` blocks) become `‹redacted›`.
  Evidence never leaves the machine and is never committed; that, not the redaction, is the guarantee.

## 8. Security, authority and protection

- **No network and no model at gate time** (kept). The wrapper's one-time download (§10) is the only
  network access `kh` causes.
- **`guard` is a builtin** (D32 kept, extended): it compares `.agents/keel.yml`, baselines and the
  sensor set with the base commit. New loosenings it catches: a script removed from a gate, a
  `timeout`, `ceiling` or `retries` raised, a `class` changed away from `security`, `files` narrowed, a
  `format` replaced by none, `enforcement` lowered. A loosening passes only when an ADR added since the
  base names **the loosened script by id** (`.agents/keel.yml#file-size`) or the baseline file —
  naming the whole `keel.yml` releases nothing, so one ADR cannot unlock every rule [builder]. A
  `mandatory` script cannot be loosened that way; only a superseding ADR (`Supersedes:`) approved
  through CODEOWNERS changes it (D43 kept; the approval itself is not checkable locally, as in v0.3).
  The v0.3 `type-strictness` checks (tsconfig `strict`, mypy/pyright strictness, D44) stay in `guard`.
  A baseline written through `kh measure` is still a file change: a grown row fails `guard` like any
  other, whichever tool wrote it. **Any change to the `run:` of a script that has `enforcement` set is
  treated as a loosening** and needs an ADR naming the script (D74): thresholds that live in the
  command line (`--fail-under 80`) cannot be lowered silently.
- **Authority is local** (D55): with no CI, `guard` and the gates are enforced by the pre-commit hook
  (agent-agnostic) and by Claude Code hooks. This is guidance-with-friction, not a server-side gate;
  a team that wants authority wires `kh gate` into its own CI.
- **PreToolUse protection** (`kh hook pre-tool-use`) denies agent edits to `.agents/keel.yml`,
  `.agents/keel.lock`, `.agents/bin/kh`, baselines and the hook settings unless the consequence map
  allows them, with the approved route in the reason (F3c kept, logic moved to Go).
- **Command interception** (D62): the same hook denies a Bash call whose command invokes an executable
  that appears in a declared script's `run:` (e.g. `./gradlew`, `pytest`), with the reason naming the
  scripts to use instead (`kh run test`) and "do not pipe its output". It denies, never rewrites: a
  rewrite has to parse shell (`cd x && FOO=1 mvn test | tail`) and would silently change semantics when
  wrong; a denial is visible. `kh run -- <cmd>` is the escape hatch for undeclared commands.
  **Matching is by command signature** [builder], computed the same way for each declared `run:` and
  for the agent's command, with a tokenizer that only splits — it never rewrites:
  1. split the command on `&&`, `||`, `;`, `|` and newlines (quotes respected);
  2. in each segment, drop leading `VAR=value` assignments and skip segments that are `cd …`, `export …`
     or `echo …`;
  3. the signature is the first token (basename for paths: `./gradlew` → `gradlew`), extended through
     known launchers — `npx`, `pnpm exec`, `yarn`, `bunx`, `uv run`, `poetry run`, `pipenv run`,
     `python -m`, `python3 -m`, `bundle exec`, `go run`, `make`, `bash`, `sh` — to the next
     non-option token: `npx eslint`, `python -m pytest`, `make lint`, `bash scripts/x.sh`;
  4. deny when any segment's signature equals a declared signature. So `npx eslint src` is denied when
     `lint` declares `npx eslint`, while `npx prettier` and an undeclared `make foo` are allowed.
  Anything the tokenizer cannot split (unbalanced quotes, `eval`, `$(…)` at the head) is allowed: the
  hook guides, it is not a security boundary.
- **Isolation:** `kh` runs as the user in the repository root and kills the process group on exit;
  no sandbox of its own (D71).

## 9. Two questions checked before writing

### 9.1 Is a CLI the right distribution vehicle?

| Option | Humans and git hooks | Any agent | Runtime needed | Verdict |
| --- | --- | --- | --- | --- |
| **Static binary via wrapper (chosen)** | yes | yes (shell) | none | lowest common denominator; one-time download |
| Copied bash (v0.3) | yes | yes | bash | P1 |
| Scripts run from the plugin directory | no (needs the plugin) | Claude only | bash | breaks humans and pre-commit |
| MCP server | no | MCP-capable agents | long-running process | could be an adapter over `kh` later (`kh mcp`), not the core |
| npm / pipx package | yes | yes | Node / Python | a runtime per stack; Go starts in ~2 ms (measured in the kh plan) |
| Docker image | yes | partially | Docker | heavy, slow to start, often absent |

Remaining risks of the choice: the first run needs network access to the release host
(mitigated by `KH_BINARY` and `KH_RELEASE_URL`, §10); keel's **own** repository needs a release
pipeline that builds reproducible binaries and publishes checksums — "no CI" applies to target
repositories, not to keel's release process.

### 9.2 Can two projects on one machine conflict? (D72)

| Shared thing | How v0.4 keeps projects apart |
| --- | --- |
| `kh` version | Each repo pins its own in `.agents/keel.lock`; the cache is per version (`$XDG_CACHE_HOME/keel/<version>/kh`, macOS `~/Library/Caches/keel/…`); the binary refuses to run under a different pin (exit 3) |
| A `kh` on `PATH` | Never used: Makefile, git hook and agent hooks call `.agents/bin/kh` by path |
| `KH_BINARY` set globally | Its sha256 is checked against the lock like a download; a mismatch is exit 3, never a silent run of the wrong version |
| Concurrent downloads | Download to a temp file in the cache directory, verify, then atomic rename |
| Run state and evidence | Per repository (and per git worktree) under `.agents/run/`; nothing global |
| Hooks | Written into each repository's `.claude/settings.json`; the plugin ships no plugin-level hooks (D35 kept), so nothing fires in a repository without keel |
| Interception | Matches only executables in **this** repository's `keel.yml` |
| Nested projects | `kh` uses the nearest `.agents/keel.yml` walking up from the working directory; a submodule with its own file is its own project |
| Plugin newer than a repo's pin | The `build` skill never bumps a lock silently; it proposes the upgrade and asks |

## 10. Distribution (D67, D68)

- Releases on GitHub (`cli/kh/vX.Y.Z` tags), reproducible builds (`CGO_ENABLED=0 -trimpath`, pinned Go
  toolchain), `SHA256SUMS` per release. Platforms: linux and darwin, amd64 and arm64. Windows only
  through WSL in v0.4.
- In each repository: `.agents/bin/kh`, a POSIX `sh` wrapper of a few dozen lines (the Gradle Wrapper
  / Bazelisk pattern), and `.agents/keel.lock` (`version` and one sha256 per platform). The wrapper
  resolves the cached binary for the pinned version, downloads and verifies it when absent, refuses on
  a mismatch, and `exec`s it.
- Overrides: `KH_BINARY` (a local binary, still verified), `KH_RELEASE_URL` (a mirror).
- The plugin carries no binaries; `build` writes the wrapper and the lock with the user's approval.
  `make bootstrap` runs `.agents/bin/kh version` so humans get the binary the same way.

## 13. Alternatives discarded

| Alternative | Why not |
| --- | --- |
| Keep the copied bash engine and add evidence/timeouts to it | Fixes P2's gaps but not P1 (copies and drift) |
| `kh` orchestrating the existing `.sh` sensors (the `feat/keel-cli` model) | P1 unsolved; byte-parity with `gate.sh` becomes a cost with no user |
| One parser per tool | Release per tool format change; formats cover dozens of tools with 5 parsers |
| A `{changed}` placeholder in commands | Ties commands to a keel template; the pre-commit model is established and keeps commands copy-pasteable |
| Rewriting the agent's commands in a hook (rtk style) | Needs a shell parser; wrong rewrites are silent; the measured problem is a few commands |
| Intercepting anything that looks like a build | False positives (`grep gradle`); no parser for undeclared commands, so little gain |
| Automatic retries without limit or marking | Hide flaky tests, the opposite of a deterministic verdict |
| Committing the binary in each repository | History grows by tens of MB per upgrade; an unreviewable executable the agent could replace; still needs a platform shim |
| Binaries embedded in the plugin | 30–50 MB plugin; humans without the plugin still need `kh` |
| Deterministic `kh detect` | Owner prefers the skill's inference with confirmation |
| Using Task/mise/npm scripts as the configuration | None carries verdict metadata; would require another tool in every repository |
| Keeping the CI workflow | Owner: the harness is local; teams wire CI themselves |

## 14. Roadmap and acceptance

Each milestone is merged only when its acceptance holds and `make check` and `make validate` pass.

| M | Deliverable | Acceptance |
| --- | --- | --- |
| **M0 Core run** | `kh run -- <cmd>`, capture, process group, timeout, evidence store, IDs, retention, redaction, `kh show` | A command killed by timeout is `error` and leaves no child process; `cmd \| …`-free capture preserves the exit code for 0, 1, 2, 137; a planted `AWS_SECRET_ACCESS_KEY` value and a `ghp_` token never appear in `output.log` or stdout; retention keeps exactly 50 runs |
| **M1 Config and gates** | `.agents/keel.yml` schema and strict validation, scripts short/expanded, gates, `files`/`pass_files`/`--all`, `changes`, `requires`, lock, `kh validate`, `kh gate`, `kh measure` | With `changes: staged`, a file modified only in the work tree is not in scope; no matching file → `skip`; a missing `gitleaks` on a `security` script fails the gate, a missing linter on a `heuristic` one is reported as skipped; `--all` batches past `ARG_MAX` and merges one verdict; every invalid config in a fixture list exits 3 |
| **M2 Formats** | `junit`, `sarif`, `checkstyle`, `eslint-json`, `errorformat`, generic reduction, text and `--json` output | Fixtures from real tool output (Gradle, Surefire, pytest, vitest, eslint, gitleaks, ruff, tsc, mypy) parse to the expected findings; a non-zero exit with an unparseable report is never `pass`; output ≤ 40 lines with the cap announced |
| **M3 Builtins and baselines** | `guard` over `keel.yml`, TSV baselines, `enforcement`, `file-size`, `code-language`, `folder-layout`, `pattern`, `architecture-grep`, `test-presence`, `dependencies`; retries with flaky marking | Every loosening in §8 fails `guard` without an ADR and passes with one; `mandatory` fails even with one; the D-1 reproduction (a baseline row appended by the agent) fails; a pass on retry 2 is `pass (flaky: 2/2)` |
| **M4 Hooks** | `kh hook pre-tool-use` (protection + interception), `kh hook stop` (fingerprint, lock, failure relay), pre-commit configs | `./gradlew test` from the agent is denied with `kh run test` in the reason when `test` is declared; an undeclared `make foo` is allowed; editing `.agents/keel.yml` is denied; Stop hook relays a failing gate and stays silent on an unchanged green tree |
| **M5 Check and distribution** | `kh check` (§11 list), release pipeline, wrapper, `KH_BINARY`, `KH_RELEASE_URL` | Two repositories pinned to different versions run side by side; a tampered cached binary or `KH_BINARY` is refused; reproducible `make dist` (byte-identical twice); wrapper works on bash-less `sh` |
| **M6 Plugin integration** | `build`, `rules`, `assess` write and read `keel.yml`; `assets/core` bash engine removed; v0.4.0-rc | Plugin suites green; no copied engine file left in a fresh install; the tool eval cases runnable against v0.4. **E3 itself (paid, owner's machine, D50) is an owner step after M6**, not part of the executor's acceptance; v0.4.0 final waits for it |
