# Catalog - what the engineer knows

One entry per rule keel can propose. Every entry has the same six labels: **Questions** (what to
ask), **Measure** (how to read the as-is state with `measure.sh`), **Default** (how the proposal is
derived), **Why** (justification with sources), **Sensor** (what enforces it, per stack, and its
class) and **Opinion** (where the default is judgement, not fact). In brownfield, derive the default
from the measured distribution (the next round number at or above p90, never below p75); in
greenfield, use the catalog default. Say which of the two you did.

Rules are written to topic files (`docs/architecture.md`: `architecture`, `folder-layout`;
`docs/conventions.md`: `file-size`, `code-language`, `adopted-patterns`; `docs/testing.md`:
`testing-strategy`), with parameters in `.agents/rules/<id>.env`.

## file-size

**Questions**: Is there a size you already hold files to? Are generated or vendored files excluded?
**Measure**: `bash "${CLAUDE_SKILL_DIR}/assets/measure.sh" file-size` gives files, p50/p75/p90, max and the `over:N` buckets.
**Default**: brownfield, the next round number at or above p90 and not below p75 (e.g. p90 = 240, so 300); greenfield, 300 lines.
**Why**: ESLint's `max-lines` rule defaults to 300 (https://eslint.org/docs/latest/rules/max-lines). Tool defaults disagree widely (Pylint's `max-module-lines` is 1000, Checkstyle's `FileLength` 2000), and no study measures an optimal size for agents; the case for a limit is that a short file is read whole and tends to hold one responsibility. Say so when proposing it.
**Sensor**: `file-size` (agnostic, `git ls-files` + `wc -l`), class heuristic, TSV baseline (`.agents/baselines/file-size.tsv`).
**Opinion**: the exact number is opinion; 300 is a convention, not a measurement.

## folder-layout

**Questions**: Which directories hold which kinds of files? Are there files that may live anywhere?
**Measure**: `measure.sh tree 2` shows the current directory shape.
**Default**: the layout the measured tree already shows, as `ALLOWED` path patterns; greenfield, the layout of the approved architecture style.
**Why**: a predictable layout lets an agent place a new file without searching (https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html on keeping a stable codemap).
**Sensor**: `folder-layout` (path patterns over `git ls-files`), class correctness, TSV baseline when adopted late.
**Opinion**: strictness is opinion; start permissive and tighten.

## architecture

**Questions**: Is there a layering you intend (hexagonal, layered, clean, modular)? Which packages are the domain? Which framework imports must stay out of it?
**Measure**: `measure.sh imports <java|kotlin|python|ts> <prefix>` gives the real dependency matrix; `measure.sh framework-imports <path>` counts framework imports inside the domain.
**Default**: brownfield, the dependency direction the matrix already shows, with violations frozen; greenfield, the style's template map below.
**Why**: ArchUnit's `onionArchitecture()` is "also known as Hexagonal Architecture or Ports and Adapters", and `FreezingArchRule` records existing violations and reports only new ones (https://www.archunit.org/userguide/html/000_Index.html). dependency-cruiser has `depcruise-baseline` with `--ignore-known` (https://github.com/sverweij/dependency-cruiser). import-linter has `ignore_imports` (https://import-linter.readthedocs.io/en/v2.0/contract_types.html).
**ArchUnit and the JDK**: an ArchUnit release older than the project's Java version imports no class and every rule passes without checking anything (seen with ArchUnit 1.3.0 on Java 25 bytecode). Pick a release that supports the project's JDK. In brownfield, `render.sh` adds the guard rule `classes_are_analysed`, which fails in that case; in greenfield every rule gets `.allowEmptyShould(true)`, so packages with no code yet do not fail.
**Sensor**: `architecture` runs the native tool generated by `render.sh` from `.agents/rules/architecture.env` (ArchUnit for Java/Kotlin, dependency-cruiser for TS/React, import-linter for Python); class correctness, native baseline. `architecture-grep` is the fast fallback over the same map (TSV baseline) when the native tool exceeds the fast budget, which then moves to `scripts/sensors/slow/`.
**Opinion**: the style choice. The maps:

| Style | Layers (outer may depend on inner) | Notes |
| --- | --- | --- |
| hexagonal | adapters -> application -> domain | `onionArchitecture()`; domain imports no framework |
| layered | web -> service -> repository | `layeredArchitecture()`; no upward calls |
| clean | frameworks -> adapters -> use cases -> entities | one extra ring over hexagonal |
| modular | modules depend only on each other's public API | one slice per module |

Frameworks forbidden in the domain, per stack: Java/Kotlin `org.springframework`, `jakarta.persistence`, `javax.persistence`; Python `django`, `flask`, `fastapi`, `sqlalchemy`; TS/React `express`, `@nestjs`, `react`.

## code-language

**Questions**: In which natural language must identifiers and comments be written? Is user-facing text in another language (it is ignored)?
**Measure**: `measure.sh language pt.txt` gives files, flagged words and the top 10 words.
**Default**: English for identifiers and comments; string literals ignored.
**Why**: opinion, not measurement: one language for names keeps search and naming consistent. Back it with the measured count of flagged words, and do not claim more than that.
**Sensor**: `code-language` (non-ASCII letters plus a stop-list; `stoplists/pt.txt` ships), class heuristic, TSV baseline.
**Opinion**: whether to enforce it at all is the team's call.

## testing-strategy

**Questions**: What do tests look like today (unit, integration, e2e)? Is a coverage or mutation tool configured? How slow is the suite?
**Measure**: `measure.sh tests` gives main, test, unit, integration, e2e, untested_main, `mutation_tool` and `coverage_tool`.
**Default**: per style, hexagonal: domain = unit tests without the framework; adapters = integration tests (e.g. Testcontainers); few end-to-end tests. Mapping of main to test files by the project's convention; diff coverage at least 80 %; mutation score at least 60 % on changed files, raised as the baseline improves.
**Why**: the test pyramid (https://martinfowler.com/articles/practical-test-pyramid.html); mutation testing checks that tests assert something, which matters because AI-generated tests are not yet trustworthy by default (https://martinfowler.com/articles/harness-engineering.html).
**Sensor**: fast `test-presence` (class heuristic, TSV baseline); slow `mutation` and `diff-coverage` via `make gate-slow` (class correctness). Tools per stack: JVM PIT (https://pitest.org) + JaCoCo; TS/React Stryker (https://stryker-mutator.io) + lcov; Python mutmut (https://mutmut.readthedocs.io) + coverage.py. Integration and e2e suites stay the project's own targets, cited in `AGENTS.md`.
**Opinion**: the thresholds and the per-layer test types.

## adopted-patterns

**Questions**: Which patterns does the team already use that an agent would not guess (a result type, a logging wrapper, a naming scheme)?
**Measure**: read the code; there is no automatic measurement.
**Default**: record only patterns the user confirms, with `ORIGIN=discovered` in the rule's env file.
**Why**: Gloaguen et al. found that tool instructions and non-standard conventions are followed while repository overviews do not help (https://arxiv.org/abs/2602.11988).
**Sensor**: inferential (no sensor). When a pattern has a syntactic form, promote it to an ast-grep (https://ast-grep.github.io) or semgrep (https://semgrep.dev) rule and a sensor.
**Opinion**: which patterns deserve a rule.
